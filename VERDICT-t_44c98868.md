## ДЕФЕКТ 1 (блокирующий, регрессия) — свой файл в КОРНЕ обменника удалить нельзя

`hermes_acl_results.py:718-721` `require_exchange_removal`:

```python
relative = resolved.relative_to(exchange)
foreign_folder = bool(relative.parts) and relative.parts[0] != slug
```

Для файла в корне обменника `relative.parts[0]` — это **имя самого файла**, а не папка. Условие
считает такой файл «чужим подкаталогом» и отказывает 403 **всегда**, даже когда автор — сам
вызывающий. Journal-строка не спасает: `foreign_folder` проверяется первым и замыкает решение.

Проба E7/E8 (реальный роутер, HEAD кандидата):

```
E7  alice's OWN pre-existing exchange-root file (no journal row)
    DELETE shared/alice-legacy.txt -> HTTP 403: Only the user who created this exchange file may delete it
E8  journal author = 'person/alice'
    DELETE again -> HTTP 403: Only the user who created this exchange file may delete it
E9  DELETE shared/person_alice/mine.txt -> HTTP 200   (внутри своей папки — работает)
```

На базе (`7e7361e0`, те же пробы, E7): `DELETE shared/alice-legacy.txt -> HTTP 200`.
**Это регрессия**: до правки человек мог удалить свой файл из корня обменника, теперь — нет.
Практический вес: корень обменника — это ровно та раскладка, в которой лежат **все файлы,
созданные до этой правки**; правка запирает их авторов.

Это же противоречит собственному заявлению отчёта (PROGRESS.md §Правило п.3: «Свой — можно»).
Ни один из 21 теста этого не ловит: `TestSiblingWriteRoutes` удаляет только **чужой** файл и только
в чужой папке; теста «свой файл в корне удаляется» нет.

**Минимально достаточно:** решение «свой/чужой» для корневого файла принимать по авторству
(journal), а не по `parts[0]`; «чужой подкаталог» проверять только когда `len(relative.parts) > 1`.
Тест: свой файл в корне удаляется 200; чужой файл в корне (journal другого субъекта) — 403;
чужой подкаталог — 403 (сохранить).

## ДЕФЕКТ 2 (блокирующий, регрессия) — редирект стоит ДО проверки «по этому пути уже каталог»

`hermes_cli/web_routers/files.py:883-902` `_managed_write_target`: сначала
`exchange_write_target()` переписывает путь, и только потом идёт
`if target.exists() and target.is_dir(): 409`.

Когда запрошенный путь — существующий каталог (корень обменника, чужой подкаталог), редирект
превращает его в **новое несуществующее имя** внутри своей папки, проверка каталога не срабатывает,
и роут создаёт файл с именем каталога.

Проба E15, один и тот же скрипт на кандидате и на базе:

```
кандидат:  upload path=shared              -> HTTP 200, создан ФАЙЛ shared/person_alice/shared
           upload path=shared/person_bob   -> HTTP 200, создан ФАЙЛ shared/person_alice/person_bob
база:      upload path=shared              -> HTTP 409 A directory already exists at that path
           upload path=shared/person_bob   -> HTTP 409 A directory already exists at that path
```

То есть guard `is_dir` в `_managed_write_target` стал мёртвым для любого перенаправленного пути, а
«загрузить в каталог» вместо ошибки молча создаёт мусорное имя. Дополнительно: запрос на запись
в чужой **каталог** больше не получает ни 403, ни 409 — он «успешно» создаёт файл-двойник.

**Минимально достаточно:** проверку «путь — существующий каталог» выполнять по **запрошенному**
пути (до редиректа) либо после редиректа проверять и исходный путь тоже; тест: `upload path=<exchange root>`
→ 409 и никакой новый файл; `upload path=shared/person_bob` → 409/403 и никакой новый файл.
