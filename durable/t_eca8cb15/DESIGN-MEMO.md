## 1. Границы системы

### 1.1 Что живёт в процессе шлюза

Один процесс, один цикл событий (`uvicorn`, `asyncio`). В нём одновременно:

| Компонент | Роль | Пишет состояние? |
|---|---|---|
| FastAPI/Starlette-приложение (`web_server.app`) | HTTP + WebSocket панели | да, через маршруты мутаций |
| Диспетчер доставки (`gateway/`) | доставка сообщений платформ | да |
| Telegram-поллинг | приём апдейтов | да |
| Планировщик (`cron/`) | запуск задач | да |
| Сессия чата / PTY (`PTY_REGISTRY`, `web_routers/chat_ws.py`) | интерактивный чат | да (через чат-события) |
| Кэш статуса (`web_status_cache.py`, TTL+single-flight) | чтение | нет |
| Пул чтения (`hermes_state_readpool.py`) | чтение | нет |

**Что разделяется между процессами (если бы их было N):** `state.db`, `shared-state.db`
(SQLite, WAL), файлы профилей (`~/.hermes/profiles/*/…`), `gateway.lock` / `gateway.pid`
(аренда владения), control socket, in-memory-состояние ASGI (`app.state.event_channels`,
`event_lock`, `pty_active_session_files`, `chat_argv_lock`, `session_authority`) — **последнее
не разделяется вообще** и является главным техническим препятствием для A/B (§4).

### 1.2 Собственные замеры: где реальный потолок

Двухпроцессная схема (сервер в своём процессе — клиент не делит с ним GIL), живой `uvicorn`,
временный `HERMES_HOME`, 200 сессий × 8 сообщений. `probes/probe_client.py` →
`probes/twoproc_current.json`.

Латентность одного запроса и отзывчивость цикла событий (лёгкий `/api/health`, запускаемый
через 50 мс после начала залпа; рост = признак блокировки цикла):

| маршрут | n=1 p50 | n=8 p50 | n=8 max | n=16 p50 | health-проба при n=16 |
|---|---|---|---|---|---|
| `GET /api/status` | 3,3 мс | 23,2 | 23,3 | 49,6 | **9,0 мс** |
| `GET /api/sessions` | 14,3 | 121,1 | 159,4 | 325,2 | **15,2 мс** |
| `GET /api/sessions/{id}/messages` | 11,5 | 55,8 | 69,0 | 145,0 | **2,9 мс** |
| `GET /api/sessions/search` | 34,2 | 820,1 | 850,4 | 1461,0 | **40,8 мс** |

Чтение этого:

1. **`/api/status` больше не блокирует цикл.** n=16 даёт 49,6 мс на запрос и пробу 9,0 мс.
   Кэш + single-flight из t_f4d564cb уже сделали своё: работа на запрос — единицы миллисекунд,
   роста «в N раз» нет (3,3 → 49,6 при 16× нагрузке ≈ линейная деградация от накладных расходов,
   не сериализация 2-секундной работы).
2. **Потолок — чтения хранилища.** `search` даёт 34,2 мс одиночно и 1461 мс при n=16 —
   суперлинейно (43×), и проба цикла при этом растёт до 40,8 мс. Это GIL + CPU на SQLite,
   а не блокировка I/O: больше процессов это **не ускорит** внутри одного запроса, но и
   параллелизм по процессам здесь тоже не поможет — каждый запрос всё равно считает свой поиск.
3. **Ни один маршрут не «ждёт 2,0 с» сериализованно** на этой ревизии. Исходная постановка
   («8 запросов по 2,0 с по очереди») относилась к состоянию **до** t_f4d564cb; на текущей
   ревизии одиночный warm status — 3,3 мс.

## 2. Единственный писатель: что уже есть в коде

Установлено чтением, не предположением:

- **Аренда владения профилем.** `gateway/runtime_ownership.py`: `OwnershipConflict`,
  `exclusive_maintenance(homes, purpose=…)` берёт `flock` на `<home>/gateway.lock`;
  `live_runtime_owner(home)` возвращает PID живого владельца. Текст отказа:
  `Exclusive maintenance refused: … Drain and stop the gateway, then retry.`
  (`gateway/runtime_ownership.py:350`).
- **Отдельный дашборд не пишет сам.** `hermes_cli/web_server_sessions.py:277`
  `_mutate_via_gateway_owner` → `client.rpc('session.mutate', …)` через control socket;
  `_mutate_offline_store` (строка 154) исполняется **только под арендой** и открыто говорит:
  «Runs under the exact owner lock (409 while any gateway owns the store, **never a second
  writer beside it**)».
- **Подтверждено замером.** `probes/writes.json`: при 2+ одновременных записях из одного
  процесса второй и последующие получают
  `HTTP 409/503: owner_unavailable: starting: Exclusive maintenance refused: Gateway runtime
  already owns profile …`; успешных записей — ровно 1 за раунд, и все они долетают до БД
  (`renamed_count` > 0). То есть **сериализация записи — не дефект, а инвариант**.
- **Пул чтения.** `hermes_state_readpool.py` (t_f8450188): 16 хэндлов, TTL 120 с, после t_f8450188
  — 40 чтений на 1 `connect` (было 20/40). Чтение уже параллельно и не мешает писателю.

**Следствие для выбора варианта:** требование карточки «один писатель» не нужно строить — оно
уже построено и проверено. Любой вариант A/B обязан его **сохранить**, иначе нарушит
существующий инвариант, на который опираются mutex-семантика, receipt-транзакции и
`owner_unavailable` в 17 локалях.

## 3. Сравнение вариантов

### A. Вынос HTTP-слоя в отдельный процесс (API-процесс только читает + проксирует действия)

| | |
|---|---|
| **Цена** | API-процессу нужны: своё ASGI-состояние для WS (`event_channels`, `event_lock`, `pty_active_session_files`, `chat_argv_lock`), мост всех чат-событий из процесса шлюза в API (сейчас события рождаются **в том же** процессе, где `chat_ws.py`), проксирование каждого действия по control socket. Затронуто: ~40 эндпоинтов действий + весь `chat_ws.py` + `PTY_REGISTRY`. |
| **Риск** | Высокий. События чата — критерий приёмки «события доходят с той же полнотой»; при двух процессах это уже не свойство, а протокол, который надо строить и доказывать. WS-буферы (`buffer_cap=1 MiB` на `PtySessionRegistry`) живут в процессе, который держит PTY. |
| **Сложность откатa** | Средняя: флаг «не запускать API-процесс» возвращает старое, но состояние (WS, PTY) уже разъехалось — при переключении на живом сервере пользователь теряет PTY-сессии. |
| **Что даёт** | Параллельность без общей памяти. **Но** §1.2 показывает: цикл событий статуса уже не горлышко, а `search` при n=16 — 1461 мс из-за CPU+SQLite, что второй процесс не уменьшит. |

**Вердикт: отклонён.** Плата — протокол событий и PTY — больше выигрыша, который замер не
показывает.

### B. N воркеров uvicorn (SO_REUSEPORT) с общим SQLite

| | |
|---|---|
| **Цена** | Все N воркеров получают собственное `app.state` → каждый WS-клиент привязан к одному воркеру, а событие, рождённое в другом, до него не дойдёт **никогда** без внешней шины. `PTY_REGISTRY` — модульный глобал (`web_server_chat.py:51`), то есть у каждого воркера свой реестр PTY: тот же чат даст разные PTY в разных воркерах. Плюс нагрузка на писателя. |
| **Риск (доказан практикой из постановки)** | Несколько писателей в SQLite → starvation чекпоинтов WAL. В нашем коде это **уже запрещено** арендой (§2): второй воркер на том же home получит `Exclusive maintenance refused`. Чтобы B заработал, аренду пришлось бы **ослабить** — то есть снять инвариант, который сейчас защищает `state.db`. |
| **Сложность откатa** | Низкая технически (`workers=1`), но откат **не возвращает** согласованность без рестарта. |
| **Что даёт** | Единственное реальное преимущество — обход GIL для CPU-работы (`search`). |

**Вердикт: отклонён.** Противоречит существующему инварианту единственного писателя и ломает
WS/PTY, которые нельзя разнести без новой шины.

### C. Один процесс, обработчики неблокирующие + семафор

| | |
|---|---|
| **Цена** | Правка 8 локаторов из §1.3 на `asyncio.to_thread` (образец — 37 существующих). Полный список файлов и функций — §5. |
| **Риск** | Наименьший: нет новых процессов, нет новой сериализации состояния, WS/PTY остаются в том же процессе, единственный писатель не трогается. |
| **Сложность откатa** | **Наименьшая**: одна настройка конфига; правки аддитивные, каждый `to_thread` откатывается независимо; поведение до/после отличается только тем, что цикл не блокируется. |
| **Потолок** | Ограничен GIL и CPU: `search` n=16 всё равно ~1,4 с. Семафор (`anyio.CapacityLimiter`) не даёт пулу потоков съесть память. |

**Вердикт: выбран (C).** Плюс честная фиксация потолка: **этот вариант не ускоряет CPU-тяжёлый
поиск**; если он станет проблемой, это отдельная задача про индексацию/FTS, а не про параллельность
HTTP.

## 4. Поведение при падении

| Что падает | Что теряется | Как восстанавливается |
|---|---|---|
| Один обработчик (исключение в `to_thread`) | только этот запрос | HTTP 500; остальные запросы цикла живы — **в этом и выигрыш C** |
| Пул потоков переполнен | новые запросы ждут в очереди лимитера | семафор ограничивает; ожидание в цикле не блокирует другие корутины |
| Процесс шлюза | PTY-сессии, WS-подписки, кэш статуса (in-memory) | перезапуск: `state.db` не тронут (WAL), кэш прогревается первым запросом, PTY поднимаются заново |
| Писатель (`state.db`) | ничего подтверждённого: receipt-транзакция либо коммитит, либо нет | незавершённая транзакция откатывается WAL; следующий запрос читает `runtime_revision` заново |
| Чужой процесс держит аренду | запись отвечает `409/503 owner_unavailable` (замерено) | штатное поведение, не деградация; чтение продолжает работать |

### Как система выглядит в выключенном состоянии

Выключатель — настройка конфига; при её выключении **не должно меняться ничего, кроме того, что
блокирующая работа снова идёт в цикле**:

```yaml
# ~/.hermes/config.yaml
dashboard:
  parallelism:
    enabled: false          # true = оффлоад блокирующих обработчиков в пул потоков
    max_threads: 16         # предел пула (anyio.CapacityLimiter), не больше 2× ядер
```

- `enabled: false` (и отсутствие ключа) → **ровно текущее поведение**: `to_thread` не вызывается,
  обработчик исполняется в цикле как сегодня.
- `enabled: true` → оффлоад по §1.3.
- При старте в журнал пишется одна строка: какой режим поднят, предел пула и pid/порт.
- `GET /api/status` дополнительно отдаёт `parallelism: {enabled, mode, max_threads, busy}`.

Именно поэтому C безопасен: **нет второго режима жизни состояния**, есть только то, где
исполняется работа.
